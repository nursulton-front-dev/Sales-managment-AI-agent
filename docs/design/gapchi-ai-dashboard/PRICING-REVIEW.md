# Содержание тарифов: проверка текущего кода

Проверено 1 ноября 2026 года. Пользователь уточнил: вопрос касается функциональных отличий тарифов, а не только внешнего вида. Предыдущий макет `06-billing.png` слишком сокращает содержание и не утверждён как итоговый вариант.

## Что есть в каталоге

Источник — `lib/pricing.ts`:

| START | BUSINESS | PRO |
| --- | --- | --- |
| Ответы по прайсу | Всё из START | Всё из BUSINESS |
| Лиды и диалоги | Несколько календарей | Отдельные настройки агентов |
| Запись в Google Календарь | Напоминания клиентам | Расписание специалистов |
| Передача человеку | Воронка обращений | Отчёты по направлениям |

Кроме этого заданы цена, токены и `maxAgents` (1 / 3 / 10). Но наличие строки в каталоге само по себе не доказывает реализацию функции или её ограничение тарифом.

## Что показала проверка

- `components/pricing/PricingCard.tsx` не выводит `plan.features`: видны только токены, число сотрудников и назначение плана. Это одна из причин, по которой карточки выглядят одинаковыми по возможностям.
- Существуют знания и инструкции каждого агента, квалификационные вопросы, лиды, диалоги и ручная передача общения. Эти возможности нельзя описывать как отсутствующие у продукта.
- Отдельные настройки агента уже существуют в общем API и не выделены серверной проверкой только для PRO.
- В просмотренном `app/api/agents/route.ts` и `src/db/index.ts:createAgent` лимит сотрудников по плану не проверяется. Перед продажей лимитов требуется отдельная серверная реализация с учётом параллельного создания; простого ограничения кнопки недостаточно.
- Календарь сейчас хранится как одно подключение рабочего пространства с одним выбранным `googleCalendarId`. Обещание нескольких независимых календарей требует расширения и проверки сценария.
- Найдены поля `reminderSent` и `specialistName`, но не найдена готовая отправка напоминаний или отдельный модуль расписаний специалистов. Поле в таблице не является готовой функцией.
- Готовность записи в календарь и внешних каналов следует оценивать по полному рабочему сценарию; статус подключения не доказывает автоматическую запись.
- Отдельные отчёты по направлениям не подтверждены просмотренными маршрутами. Обзор с базовыми показателями не заменяет такой отчёт.

## Как продолжить

1. Составить и согласовать матрицу возможностей: общая база для всех платных планов, отличия по масштабу, отдельные возможности старших планов.
2. Для каждой строки указать статус: реализовано; требует проверки подключения; требует разработки. Не объявлять запланированное уже работающим.
3. Уже существующие функции показать в тарифах понятными пунктами. Решить отдельно, какие из них реально должны ограничиваться тарифом: добавление подписи не создаёт серверное ограничение.
4. При выбранном разделении планов реализовать общую серверную политику доступа и лимитов. Обработка параллельных запросов, понижения тарифа и существующих объектов должна быть определена явно.
5. После согласования обновить макет карточек и компонент. Цены и коммерческие условия без отдельного решения не менять.

Естественное направление позиционирования: START — один ИИ-сотрудник и базовая обработка обращений; BUSINESS — работа нескольких сотрудников и автоматизация записи; PRO — несколько направлений и управление более сложной структурой. Это предложение для обсуждения, а не подтверждение наличия всех перечисленных возможностей.

В рамках этой передачи изменены только дизайн-документы и добавлены иллюстрации. Каталог, серверные ограничения, оплата и данные пользователей не менялись.
