## Что исправить до объявления готовности

### A. Положительная проверка webhook

Сверь фактическую Production-переменную и значение, вводимое пользователем в Meta. Проверь случайные пробелы, переносы строк, кавычки, выбранный проект и окружение, а также новый деплой после обновления. Для существующего кода приоритет имеет `INSTAGRAM_VERIFY_TOKEN`, затем `INSTAGRAM_WEBHOOK_VERIFY_TOKEN`.

Если требуется обновление значения, используй одно и то же согласованное случайное значение на сервере и в Meta. Не выводи секрет в отчеты или URL логов. После READY повтори проверку: правильный токен → HTTP 200 и точный challenge; неверный → HTTP 403. Дай результаты обеих проверок.

### B. Окружение Unified login

Подготовь точный список переменных для текущего кода. Авторизация и обмен кода сейчас требуют `INSTAGRAM_APP_ID` и `INSTAGRAM_APP_SECRET`.

- В сгенерированной пользователю панелью Meta ссылке Unified login `client_id` равен `990930946670674`.
- Configuration ID: `1865927991509771`.
- Redirect URI: `https://chorla-ai.vercel.app/api/instagram/callback`.
- Для нового потока проверь пару credentials именно Meta-приложения из этой конфигурации. Не подставляй ID/Secret отдельного прежнего Instagram Login приложения.
- Config ID сейчас имеет hardcoded fallback, но настройку следует сделать явной и проверяемой для выбранного окружения.
- App Secret вводится владельцем в защищенное окружение; не проси присылать его в переписку.

### C. Неполная миграция токенов

В `app/api/instagram/callback/route.ts` после получения любого токена безусловно вызывается `getLongLivedInstagramToken`, а в `lib/instagram/client.ts` эта функция использует `graph.instagram.com` и `grant_type=ig_exchange_token`. При отказе сохраняется срок один час. Также fallback сохраненных scopes остается `instagram_business_*`.

Это по-прежнему смешивает legacy Instagram Login и новый Unified flow. Раздели режим и тип токена явно, используй соответствующие ему правила срока действия/продления, endpoints и фактически выданные права. Не помечай System User token как часовой из-за отказа чужой схемы обмена. Проверь также путь отправки сообщений, подписки и выбор Instagram-аккаунта при нескольких выданных объектах. Mock-тест успешного Graph ответа не доказывает совместимость реального типа токена.

### D. Устойчивые повторы очереди

Ежедневный cron исправил несовместимость деплоя с Hobby, но сам по себе не обеспечивает своевременный retry после завершения функции и без новых входящих сообщений. Таймер в памяти с `unref()` не заменяет устойчивое расписание. Установленное руководство Next.js `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md` ограничивает фоновые задачи временем жизни вызова; не считай обычный отложенный callback гарантированным продолжением.

Реализуй поддерживаемый текущим хостингом механизм повторов с наблюдаемостью. Если нужен внешний сервис, подготовь конкретную конфигурацию и действия владельца; не передавай ему секрет самостоятельно. Не заявляй, что ежедневный cron решает исходный инцидент. Проверь завершение/перезапуск процесса после первого сбоя и последующий retry без новых сообщений, без повторной доставки и списания.

### E. Проверить схему БД отдельно

В коде добавлены восемь полей `telegram_business_*` в `workspaces` и таблица `telegram_business_bindings`. Их наличие в рабочей БД этой проверкой не установлено: автоматическая проверка разрешения на чтение не завершилась вовремя; последующая попытка через обычный доступ также не выполнила чтение. Это не доказательство отсутствия таблиц, но и не подтвержденная миграция.

Проверь реальную схему запросом только для чтения перед проверкой Telegram Business. Если требуется миграция, подготовь конкретный безопасный SQL и план проверки для владельца. Рабочую БД автоматически не меняй.
