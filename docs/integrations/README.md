# Каналы сообщений и чат сайта

Реализация продолжает MVP: надёжность Telegram/Instagram и устанавливаемый чат сайта. WhatsApp, Uzum Market, звонки и Bitrix24 остаются отдельными задачами. Реальный Instagram заказчика ещё не подключён.

## Что работает

- Telegram принимает сообщения только с правильным webhook-секретом. `update_id` образует устойчивый идентификатор события.
- Instagram проверяет подпись Meta и направляет сообщение только по сохранённому идентификатору подключённого аккаунта. Выбора «первой компании» нет. Неуспешная подписка на сообщения не считается подключением.
- В «Интеграциях → Сайты» владелец выбирает сотрудника, точные адреса сайтов, приветствие, заголовок, цвет, сторону кнопки и включение приёма обращений. Текст кнопок автоматически получает читаемый контраст.
- После сохранения появляется готовый `<script>` с публичным идентификатором. Настройки меняются в кабинете без замены фрагмента на сайте. Ключи моделей и каналов во фрагмент не попадают.
- Виджет изолирует оформление через Shadow DOM. Сообщения выводятся текстом, поддерживаются Enter/Shift+Enter, Escape, возврат фокуса, мобильная ширина, восстановление истории в той же вкладке и повтор отправки с прежним идентификатором.
- Сообщения сайта сохраняются в общих «Диалогах». Оператор перехватывает разговор и отвечает; посетитель получает ответ опросом раз в 4 секунды. Кабинет тоже обновляется автоматически.
- «Помогите установить» создаёт настоящее обращение в поддержке с адресами сайтов. Доступ к чужому сайту автоматически не предоставляется.
- Проверка установки фиксирует загрузку конфигурации с разрешённого адреса и время последнего запроса. Она не заменяет тестового сообщения и ответа.
- Старый сценарий записи «по ключевым словам на завтра 14:30» удалён. Каналы оплачивают только ответ ИИ (1 внутренний токен); модель получает запрет утверждать, что запись/оплата/заказ уже оформлены. Полноценная запись требует отдельного выбора и подтверждения слота.

## Установка клиентом

1. Создать и настроить ИИ-сотрудника с базой знаний.
2. Открыть «Интеграции → Сайты». Добавить точные origins, например `https://example.uz` и отдельно `https://www.example.uz`. Поддомены не разрешаются автоматически. До 10 адресов; пути, wildcard, учётные данные в URL и обычный HTTP запрещены. Для локального теста разрешён HTTP на localhost/127.0.0.1.
3. Сохранить настройки и включить приём обращений.
4. Скопировать выданный код перед `</body>` либо в настройку пользовательского кода конструктора. Достаточно одной копии.
5. Открыть сайт, нажать кнопку чата, отправить сообщение. Проверить ответ и появление переписки в «Диалогах».
6. Если сайт использует CSP, разрешить домен сервиса в `script-src` и `connect-src`. Для встроенных стилей Shadow DOM может потребоваться согласование политики `style-src` с разработчиком сайта. При блокировке сторонних скриптов/сетевых запросов установка требует настройки сайта.

Публичный домен сервиса берётся из `APP_URL`, затем `BETTER_AUTH_URL`. На реальном сайте требуется HTTPS и рабочий API-домен. Локальный origin автоматически не становится production-адресом.

## Подготовка окружения и базы

1. Использовать отдельную тестовую БД и резервную копию перед изменениями целевой БД.
2. Применить **добавочную** миграцию [widget-channels.sql](../../scripts/sql/widget-channels.sql) через SQL-консоль PostgreSQL/Neon до публикации обработчиков. Она создаёт `website_widgets`, `widget_sessions`, `channel_events`, `integration_rate_limits` и индексы, не удаляет данные. Основная схема `src/db/schema.ts` должна уже присутствовать. Повторное применение миграции безопасно.
3. Задать `DATABASE_URL`, `APP_URL`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET` (случайный, от 32 символов), выбранную модель и её ключ. Примеры переменных — `.env.local.example`.
4. Для Instagram задать app ID/secret, verify token, секрет шифрования `INSTAGRAM_TOKEN_ENCRYPTION_KEY` либо использовать `BETTER_AUTH_SECRET`. Встроенного резервного ключа больше нет. Старые токены, зашифрованные прежним резервным ключом, требуют переподключения аккаунта. Не менять ключ шифрования без плана переподключения/перешифрования.
5. Для Telegram нужен публичный HTTPS origin: подключение бота выполняется через существующий интерфейс.
6. Создать случайный `CRON_SECRET` и настроить планировщик, вызывающий `GET /api/cron/channel-events` с `Authorization: Bearer <CRON_SECRET>` каждую минуту. Можно запускать `node scripts/run-channel-worker.cjs`, передав переменные окружения планировщику. Один лишь секрет не включает расписание. На сервере нужны обработка `after()` и длительность запроса до 60 секунд.

Без `DATABASE_URL` используется отдельный локальный JSON-файл. Это только разработка в одном Node-процессе; для нескольких процессов, serverless и production нужна PostgreSQL. Сессии авторизации без БД также не переживают перезапуск.

## Повторы и восстановление

События хранятся до запуска ИИ. Счётчик последовательности и атомарный захват обеспечивают порядок в пределах диалога. Индекс разрешает только один обрабатывающийся event на диалог.

- Дубликаты webhook/отправки посетителя используют прежний event, входящее/исходящее сообщение имеют устойчивые ID.
- При явно отклонённой отправке с временной ошибкой повтор использует уже подготовленный и оплаченный ответ. Повторного обращения к модели и списания нет.
- Недоступная модель не списывает токены; назначается безопасная повторная попытка.
- До 5 попыток с увеличивающейся задержкой. В журнале показываются канал, дата, число попыток и безопасная причина без текстов переписки и секретов.
- Если процесс оборвался при генерации/списании или внешней отправке, результат может быть неизвестен. После истечения 180 секунд событие помечается «Требует проверки», диалог передаётся человеку. Автоматической повторной отправки или повторного списания нет. Сотрудник проверяет историю и при необходимости отвечает вручную; возобновление ИИ выполняется осознанно через управление диалогом.
- Повторные попытки выполняет планировщик. Открытый виджет также возобновляет свою очередь, кнопка «Проверить очередь» запускает доступные безопасные задачи компании. Неполученный остаток большого webhook-пакета сохраняется для планировщика.
- Один запрос обработчика обрабатывает до 4 разных диалогов параллельно, один event на диалог. Подбирать частоту/число вызовов нужно по реальной нагрузке. Это не обещание заданного SLA или неограниченной пропускной способности.
- Legacy-события старой Instagram-очереди автоматически не воспроизводятся: подтвердить их результат перед переносом. Аккаунт пользователя до этих изменений не был подключён; старые таблицы не удаляются.

## Защита публичного чата

Посетитель получает случайный секрет сессии на 7 дней. На сервере хранится только его хеш; он привязан к виджету и точному origin. Браузер хранит секрет в sessionStorage; при недоступном хранилище — в памяти текущей страницы. Cookies владельца не используются. Секреты не передаются в URL. Каждый запрос заново проверяет включение виджета, сайт, активность компании и сотрудника.

Лимиты общие для всех экземпляров приложения при PostgreSQL: до 100 новых сессий в час на виджет, до 10 новых сообщений в минуту на сессию и 100 на виджет, до 40 опросов истории в минуту на сессию. Заявка на помощь — не чаще одной в час на компанию. Размер публичного JSON ограничен 12 KB при чтении потока, сообщение — 4000 символами. Обновление лимитов атомарно. Origins и CORS ограничивают браузерное использование; публичный ID сам по себе не является секретом и не заменяет противодействия злоупотреблениям.

Сроки хранения переписки, событий и журналов должны быть утверждены отдельно. Автоматическое удаление истории пока не реализовано. Временные счётчики и истёкшие сессии следует очищать плановым обслуживанием; действующие лимиты считаются по отдельным временным окнам и от старых строк не зависят.

## Проверки

- `node scripts/test-widget-channels.cjs`: реальные локальные репозитории, обработчики и gateway; подставлены роли и внешние транспорты. Проверяет изоляцию, дубли, списания, порядок очереди, сбои, перехват, подписи, шифрование и отказ подключения.
- `node scripts/verify-widget.cjs`: сам запускает отдельный локальный Next-сервер, отдельный сайт клиента и локальный HTTP-ответчик модели. Проверяет установку через UI, CORS, путь сообщения и списания, ответ сотрудника, обновление без перезагрузки, смену сессии и мобильную ширину. Chrome требуется по `/opt/google/chrome/chrome`; порты 3110/3111/3112 должны быть свободны. Рабочие данные и платные модели не используются.
- `node scripts/test-widget-postgres.cjs`: отдельная локальная PostgreSQL 16, настоящие SQL Drizzle и конкурентные операции. Схема должна быть заранее применена в пустой БД с именем `widget_*`. Транспорт Neon HTTP заменён тестовым адаптером `psql`; это не проверка удалённого Neon HTTP.
- Предыдущие 14 бизнес-проверок `test-design-risks.cjs` сохраняются.
- Поддерживается `next build --webpack` / `next dev --webpack` с тем же установленным Tailwind loader. Это резервный вариант для среды, ограничивающей служебные порты Turbopack.

Итог: 46 локальных, 25 браузерных, 11 PostgreSQL и 14 прежних бизнес-проверок — 96 проверок. Типы и production-сборка через Webpack прошли. Общий ESLint: 56 ранее существовавших ошибок, 127 предупреждений; в новых и изменённых production-файлах ошибок нет. [Сводка проверки](verification.json).

Результаты: [локальные проверки](unit-verification.json), [браузер](browser-verification.json), [PostgreSQL](postgres-verification.json), [снимки](evidence/).
