# gapcha AI — аудит 5 ноября 2026

## Вердикт и границы

До исправления A01 и A02 приложение нельзя считать безопасным для публичного запуска. Аудит выполнен на текущем рабочем дереве, включая ещё не опубликованные исправления интеграций. Изменения приложения, публикация, очистка рабочей БД и отправка сообщений клиентам в ходе этого аудита не выполнялись.

Проверены основные пути авторизации, доступ компаний, административные маршруты, Telegram/Instagram, очередь сообщений, баланс и тарифы, виджет, календарь, поддержка и служебные скрипты. Это аудит исходников и изолированных обработчиков, а не подтверждение каждой функции на production. Не проверялись реальные секреты, текущие роли Meta, доставка Direct, текущий Vercel deployment, эксплуатация облачной инфраструктуры, доступность всех экранов в браузере, зависимости по внешней базе CVE и полное соответствие исходному DOCX-ТЗ.

## Подтверждённые проблемы

### A01 — Критическая: публичная выдача сессии по ID пользователя
- `lib/auth.ts:154–176`, `app/api/auth/[...all]/route.ts`.
- `login/complete-2fa` принимает userId и создаёт сессию без проверки пароля, OTP, действующей сессии или одноразового серверного разрешения. Плагин экспортирован через публичный Better Auth handler.
- Воспроизведено без сети на настоящем Better Auth handler: взята конфигурация и плагины из текущего lib/auth.ts, заменена только БД на память, создан искусственный пользователь. Запрос без Cookie, пароля и OTP получил HTTP 200 и Set-Cookie. Секреты и токен не выводились.
- Знание ID существующего пользователя позволяет войти от его имени. Проверка emailVerified далее не спасает уже подтверждённый аккаунт.
- Исправление: убрать публичный endpoint либо требовать атомарно погашаемое серверное подтверждение; выпускать сессию только после проверенного OTP. Проверить прямой HTTP-доступ, не только вызов функции из verify-code. При публикации устранения рассмотреть отзыв существующих сессий как отдельное управляемое действие.

### A02 — Высокая: обязательный код обходится стандартным входом
- `lib/auth.ts:207`, публичный catch-all auth route.
- emailAndPassword.enabled оставляет доступным стандартный sign-in/email, который выдаёт сессию сразу после пароля. Собственная форма с кодом не защищает этот альтернативный маршрут.
- Воспроизведено тем же изолированным настоящим handler: HTTP 200 и сессионная cookie без OTP.
- Исправление: применять обязательный второй этап на всех парольных путях или блокировать публичный альтернативный путь. OAuth должен иметь отдельную явно определённую политику.

### A03 — Высокая: очистка всей рабочей базы через админку
- `app/api/admin/reset/route.ts:6–64`.
- Проверка superadmin есть, однако существует пароль по умолчанию в исходниках; удаляются все компании, пользователи, сессии и даже журнал аудита. Ошибки DELETE подавляются, результат сообщает нулевые счётчики без проверки.
- Это не ограниченная очистка тестовых записей. Возможны частичное удаление и ложное сообщение об успехе.
- Исправление: отключить destructive reset на production, использовать отдельный процесс с проверенным backup, конкретными ID, транзакцией и сохранением аудита. Пароль по умолчанию удалить.

### A04 — Высокая: перебор пароля не ограничен собственным login route
- `app/api/auth/login/route.ts:39–101`.
- Ограничитель применяется только после успешной проверки пароля. Неверные попытки возвращаются раньше и не учитываются. Лимитер Better Auth не покрывает отдельный Next.js маршрут автоматически.
- Исправление: общий атомарный лимит по аккаунту и источнику до дорогой проверки пароля, без раскрытия существования аккаунта.

### A05 — Высокая: приостановка Telegram не останавливает уже принятую очередь
- `lib/server/channels/processor.ts:25–78`, `app/api/integrations/telegram-business/toggle/route.ts`.
- Входящий webhook проверяет enabled/connected, но worker перед отправкой проверяет только наличие bot token. Не проверяет telegramBusinessEnabled, Connected, CanReply и соответствие текущего connection ID сохранённому в событии.
- Если выключить канал после получения сообщения, queued/prepared ответ может уйти после паузы. Отключение в Telegram может остановить его внешне, но выключение на сайте само по себе не останавливает.
- Исправление: повторная проверка актуального канала перед генерацией и отправкой, отмена/приостановка ожидающих событий.

### A06 — Высокая: ручной ответ выбирает не тот Telegram-транспорт
- `app/api/conversations/[id]/route.ts`, ветка POST Telegram.
- Business-режим выбирается по текущему workspace, а не по происхождению конкретного диалога. При наличии собственного бота и Business-подключения ответ в диалог собственного бота направляется через service bot и business_connection_id.
- Исправление: хранить транспорт и connection ID у диалога; отправлять через исходный канал и проверять принадлежность компании.

### A07 — Высокая: после неопределённой отправки Instagram выполняется вторая отправка
- `lib/instagram/client.ts:352–402`.
- Ошибка/timeout запроса Facebook Graph проглатывается, затем выполняется POST Instagram Graph. Первый запрос мог уже доставить сообщение. Кроме того, причина отказа первого API теряется.
- Исправление: выбирать один транспорт по источнику токена; при неопределённом результате переводить в ручную проверку. Не переключать API после потенциального внешнего эффекта.
- Сам факт дубля на Meta не воспроизводился; опасная ветка подтверждена исходниками.

### A08 — Высокая: нет связи между списанием и подтверждённой доставкой
- `lib/ai/gateway.ts:209–226`, `lib/server/channels/processor.ts:49–90`.
- Баланс списывается при генерации до доставки. Затем оператор может перехватить диалог, канал отключиться или отправка окончательно отказать. Возврата/резервирования и идентификатора события в финансовой операции нет.
- Атомарность баланса и ledger реализована, но не весь цикл ответа. Если продукт продаёт доставленные ответы, текущая семантика неверна; если генерации — это нужно явно сообщить пользователю.
- Исправление: резервирование, идемпотентное подтверждение/возврат с eventId и документированная политика неопределённой доставки.

### A09 — Высокая: небезопасные границы служебной очистки
- `scripts/db-cleanup-dry-run.cjs:196–280`.
- Скрипт уже улучшен: требует workspace, manifest, backup и выполняет DELETE в транзакции. Старое замечание об отсутствии этих ограничений больше не актуально.
- Однако наличие backup проверяется только для conversations/messages, не для остальных удаляемых сущностей. DELETE фильтруется по ID без дополнительного workspaceId. После операции статус безусловно становится active, даже если до неё компания была suspended. Maintenance не синхронизирован с уже работающими обработчиками и всеми API записи.
- Исправление: проверить принадлежность и backup каждого ID, сохранить исходный статус, надёжно остановить записи и workers, затем удалять ограниченным запросом. Скрипт не запускался.

### A10 — Средняя: Telegram bot token хранится открытым вопреки интерфейсу
- `app/api/agents/route.ts` POST/PATCH сохраняют body.tgBotToken напрямую; `src/db/index.ts:494` записывает updates без шифрования.
- Интерфейс обещает шифрование в БД (`app/dashboard/integrations/page.tsx:1409`, wizard:826). Маскирование публичного ответа есть; это не шифрование хранения.
- Исправление: единое шифрование секретов с безопасной миграцией и отсутствие токенов в backup/logs. Пароли и bot token в browser draft не обнаружены.

### A11 — Средняя: срок тарифа не применяется к работе ИИ
- `lib/ai/gateway.ts`, `lib/server/channels/processor.ts`, `lib/server/widget/security.ts`.
- subExpiresAt используется для отображения, но эти пути проверяют active/баланс без срока. Просроченный trial/платный тариф с остатком продолжает работу.
- Исправление: определить продуктовую политику остатков и применять общий серверный entitlement check, одинаковый для всех каналов.

### A12 — Средняя: лимит сотрудников обходится конкурентными созданиями
- `app/api/agents/route.ts:56–73`.
- Чтение количества и INSERT раздельные. Два одновременных запроса могут увидеть последнее свободное место и оба создать сотрудника.
- Исправление: сериализация по workspace в транзакции либо атомарная квота. Обычный тест одного запроса недостаточен.

### A13 — Средняя: публичная поддержка доверяет указанному email
- `app/api/support/public/route.ts:6–25, 74–84`.
- Неавторизованный отправитель может создать обращение от email владельца чужой компании. Неизвестный email прикрепляется к первой компании в БД. Лимит хранится в памяти одного процесса, номер тикета строится по общему count.
- Последствия: поддельные обращения, неверная принадлежность, гонки номера, слабая защита от спама.
- Исправление: отдельная очередь неподтверждённых публичных обращений, подтверждение адреса/явный anonymous sender, серверный общий лимитер и sequence для номера.

### A14 — Средняя: диагностика публично раскрывает внутренние детали
- `app/api/health/route.ts`.
- Без авторизации возвращает имя БД, все названия таблиц, часть API-ключа и сырые ошибки. Каждый вызов делает запросы к БД.
- Исправление: публичный минимальный health, подробности только администратору, без частей ключей и сырых ошибок; отдельная readiness-проверка с ограничением частоты.

### A15 — Средняя: тесты авторизации подменяют конфигурацию приложения
- `scripts/test-login-2fa.ts:164–222`, `scripts/test-auth-security.ts:207–270`.
- Тесты создают собственный login2FAPlugin и betterAuth, затем setTestAuth. Положительные результаты не подтверждают безопасность публичного production handler. A01/A02 не покрыты.
- Исправление: тестировать конфигурацию и публичный HTTP handler приложения на изолированной БД; отрицательные проверки всех альтернативных маршрутов обязательны.

### A16 — Средняя: тестовый скрипт пишет в БД из .env.local
- `scripts/test-telegram-account-dialog.cjs:21` и операции INSERT/DELETE далее.
- Скрипт сам берёт DATABASE_URL локального проекта, создаёт/удаляет записи. Нет обязательного изолированного TEST_DATABASE_URL с проверкой назначения.
- Исправление: запрет неявного production URL, изолированные fixtures и проверка тестовой БД до первой записи. В ходе аудита не запускался.

### A17 — Средняя: отказ планировщика может выглядеть как успех
- `.github/workflows/channel-cron.yml`, `vercel.json`.
- При отсутствующем CRON_SECRET workflow пишет warning и завершается с exit 0. В Vercel резервный cron — раз в сутки. Наличие действующего секрета/запусков сейчас не проверялось.
- Исправление: отсутствие обязательной настройки должно давать ошибку, нужен контроль возраста старейшего события и уведомление о задержке. setTimeout.unref в worker не является подтверждением надёжной доставки после завершения HTTP-запроса.

## Функциональные ограничения, которые нельзя выдавать за готовые возможности

- В основной цепочке сообщений gateway возвращает только текст, isBooking=false. Автоматическое создание лида/подтверждённой записи из разговора не подключено к этой цепочке. Наличие деклараций tools и test-event API не означает действующую автоматическую запись. Необходимо согласовать UI-обещания с реализацией.
- subscribe и topup намеренно возвращают 503: онлайн-оплата отсутствует. Самостоятельная смена тарифа без подтверждённого платежа правильно запрещена.
- Пользовательский контекст разрешает владельца по email и superadmin; полноценного членства команды в этом пути нет. Наличие вкладки «Команда» не подтверждает роли сотрудников.
- Русский текст жёстко задан во многих dashboard-компонентах; полный узбекский интерфейс этой проверкой не подтверждён.
- Meta data-deletion callback очищает токен и флаги, но не сообщения и профиль; для полноценного удаления данных нужен отдельный проверяемый процесс. Это техническое наблюдение, не юридическое заключение.

## Что уже защищено

- Основные пользовательские API получают серверную сессию; лиды и сотрудники проверяют принадлежность workspace. Для superadmin существуют явные исключения, их стоит согласовать с политикой аудита поддержки.
- Неподтверждённый email не получает компанию через session resolver.
- Из публичных workspace/agent ответов исключены основные токены.
- Баланс и запись финансового журнала меняются одним SQL-запросом с защитой от отрицательного остатка.
- Очередь имеет дедупликацию, сериализацию разговора и перевод неопределённых операций в ручную проверку. A07 нарушает эту гарантию внутри транспортного адаптера.
- Виджет проверяет разрешённый origin, собственную visitor session, размеры запросов и квоты. Origin сам по себе не является удостоверением клиента вне браузера.
